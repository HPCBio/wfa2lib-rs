# Performance: wfa2lib-rs vs C WFA2-lib

A snapshot of Rust vs C [WFA2-lib](https://github.com/Marco-Sola-Lab/WFA2-lib)
on three machines, at wfa2lib-rs `fc51088` (2026-10-16) and C WFA2-lib
`3282f83`. It is pinned to these commits; later changes are tracked in
HPCBio/wfa2lib-rs#31.

## Method

[`bench/sweep.py`](../bench/sweep.py) runs both `align_benchmark` tools on
301 configurations: every distance metric with high, med, low and ultralow
(BiWFA) memory, score-only and CIGAR, ends-free and extension spans, and the
heuristics (WF-adaptive, X-drop, Z-drop, static and adaptive banding). Each
case is run 3 times, and the best time is kept. Times are `Time.Alignment`
as each tool reports it.

- **Rust**: built with `target-cpu=native`.
- **C**: built without `-march=native`, so it uses its portable kernels.
  This is the main comparison, and the build the output checks use.
- **C with `-march=native`**: also measured and enabled using C's AVX2/AVX-512
  kernels on x86, which appears to gain the most on the Xeon.
- **On macOS,** to make sure timings are comparable across platforms, C's own
  timer is replaced with `clock_gettime` ([`build_c.sh`](../tests/differential/build_c.sh)). C's Mach clock 
  calls cost about 1.3 µs per alignment inside the timed interval, which made C 
  look up to 6× slower on short reads.

Datasets are generated with fixed seeds, so every machine aligns the same pairs:

| Dataset | Pairs | Length | Differences |
|---|---|---|---|
| `s150_2` | 50,000 | 150 bp | 2% |
| `m1k_5` | 20,000 | 1 kb | 5% |
| `m1k_20` | 5,000 | 1 kb | 20% |
| `m1k_indel` | 2,000 | 1 kb | 5%, plus 5 indels of up to 50 bp |
| `l10k_5` | 300 | 10 kb | 5% |
| `m2k_flank` | 300 | 2 kb | 5%, plus random 200 bp flanks (span cases) |

The M2 run is labelled `c43fd1a-dirty`. Its source is identical to
`fc51088`; the uncommitted change was the macOS timer fix in `build_c.sh`.

## Notes

- **Output:** Rust's output is byte-identical to C's in all 301 cases on
  every machine. C built with `-march=native` differs from generic C in 26
  ends-free cases on x86, as expected (HPCBio/wfa2lib-rs#34).
- **Where Rust is fastest:** med/low memory (vectorized, fused piggyback
  kernels), ends-free and extension alignments, and gap-affine 2-piece BiWFA
  (vectorized breakpoint scan).
- **Apple M2:** high-memory score and CIGAR are close to parity
  (about 0.97×). Apple clang compiles C's kernels well on ARM.
- **Intel Xeon Gold 6150:** results are less favorable than on the EPYC.
  It's an older design (Skylake-SP, 2017, against Zen 3 in 2021). Every
  case is slower there than on the EPYC for both tools, but Rust more so:
  its median time is 1.47× its EPYC time, against 1.29× for generic C and
  1.24× for C with `-march=native`. Two things stand out:
  - Gap-affine 2-piece CIGAR in high memory is about even (1.0×) C's
    time (1.28× with static banding), while it is 0.77× on the EPYC. Rust
    executes the same share of C's instructions (0.66×) on both machines, so
    this is specific to how the Xeon runs that code path. It is under
    investigation in HPCBio/wfa2lib-rs#31.
  - C built with `-march=native` uses AVX-512 there, so it is the strongest
    C build of the three (median 0.94× for Rust).
  - Skylake-family CPUs are also sensitive to code alignment (the JCC
    erratum); see [Chip-specific optimizations](../README.md#chip-specific-optimizations) in the README.
- **Known gaps:**
  - 150 bp reads with med/low memory are slower than C on every machine
    (1.1–1.6×).
  - WF-adaptive edit alignments are about 1.05–1.17× C.
  - Peak memory: most cases match C, but high-memory CIGAR on long or
    divergent pairs uses up to 1.9× C's peak RSS (gap-affine 2-piece,
    `l10k_5`: 420 vs 222 MB).
  These are tracked in HPCBio/wfa2lib-rs#31.

## Reproducing

```bash
python3 bench/sweep.py                    # ~2.5 h; --quick for a short check
python3 bench/report.py target/bench-sweep/<host>-<commit> [...] > tables.md
```

`bench/sweep.py --help` lists the options, including `--offline` for
machines without network access. Run it on an idle machine.
